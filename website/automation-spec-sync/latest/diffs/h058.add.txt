This document defines the preferred MCP-AQL shape for relationship traversal and graph-oriented READ operations. Relationship queries give clients a standard way to move through adapter-defined connections without manually fetching each node one hop at a time.
The preferred operation name is query_relationships :
operation : &quot;query_relationships&quot; ,
params : {
root : {
element_type : &quot;agent&quot; ,
element_name : &quot;code_reviewer&quot;
direction : &quot;outgoing&quot; ,
relationship : &quot;uses&quot; ,
depth : 2 ,
include : [ &quot;root&quot; , &quot;relationships&quot; , &quot;graph.nodes&quot; , &quot;graph.edges&quot; ]
Parameter
Required
Starting resource for the traversal
direction
incoming , outgoing , or both
relationship
Relationship type to match
Maximum traversal depth
Optional response-section selector for root , relationships , graph.nodes , and graph.edges ; all sections returned if omitted
first / after
Optional pagination controls when traversals are large
Adapters MAY add domain-specific root identifiers or filter controls, but SHOULD keep the traversal vocabulary stable.
When pagination is supported for large traversals, the request shape remains the same:
first : 25 ,
after : &quot;cursor_rel_001&quot;
&quot;success&quot; : true ,
&quot;data&quot; : {
&quot;root&quot; : {
&quot;element_type&quot; : &quot;agent&quot; ,
&quot;element_name&quot; : &quot;code_reviewer&quot;
&quot;relationships&quot; : [
&quot;type&quot; : &quot;uses&quot; ,
&quot;direction&quot; : &quot;outgoing&quot; ,
&quot;target&quot; : {
&quot;element_type&quot; : &quot;skill&quot; ,
&quot;element_name&quot; : &quot;typescript_analysis&quot;
&quot;depth&quot; : 1
&quot;graph&quot; : {
&quot;nodes&quot; : [
&quot;id&quot; : &quot;agent:code_reviewer&quot; ,
&quot;id&quot; : &quot;skill:typescript_analysis&quot; ,
&quot;edges&quot; : [
&quot;source&quot; : &quot;agent:code_reviewer&quot; ,
&quot;target&quot; : &quot;skill:typescript_analysis&quot; ,
&quot;type&quot; : &quot;uses&quot;
If include is omitted, adapters SHOULD return root , relationships , and graph together. If include is present, adapters SHOULD limit the response to the requested sections.
relationships is the preferred flat traversal list for simple consumers that want to iterate edges in order. graph.nodes and graph.edges are the preferred graph-native shape for visualization, graph algorithms, and other clients that need explicit node/edge separation. The relationships list and graph.edges MAY describe the same connections in different shapes.
The preferred portable relationship types are:
references
triggers
composes
Adapters MAY define additional relationship types. When they do, they SHOULD document them in introspection and keep custom semantics explicit.
Adapters SHOULD document a maximum supported traversal depth.
Adapters SHOULD avoid infinite traversal by deduplicating visited nodes.
When cycles are present, adapters SHOULD still emit the edge but MUST prevent unbounded expansion.
Adapters SHOULD advertise relationship-query support through operation detail metadata:
&quot;relationship_capabilities&quot; : {
&quot;supported&quot; : true ,
&quot;directions&quot; : [ &quot;incoming&quot; , &quot;outgoing&quot; , &quot;both&quot; ] ,
&quot;relationship_types&quot; : [ &quot;uses&quot; , &quot;extends&quot; , &quot;references&quot; , &quot;triggers&quot; , &quot;composes&quot; ] ,
&quot;max_depth&quot; : 3
Collection Querying defines how record-level fields and pagination compose with collection-style responses.
Operations documents the common request and response conventions used by query_relationships .
