Abstract
This document specifies the requirements and behavior of MCP-AQL adapter generators. An adapter generator takes a schema definition as input and produces compliant adapter code with required licensing artifacts and provenance information.

1. Overview
1.1 Purpose
Adapter generators automate the creation of MCP-AQL adapters from schema definitions. This ensures:
Consistency - All generated adapters follow the same patterns
Compliance - Licensing and attribution requirements are met
Traceability - Provenance information enables debugging and auditing
Productivity - Developers focus on business logic, not boilerplate
1.2 Generator Types
Description
Use Case
Schema-to-Code
Generates adapter source code from schema
Development workflow
Schema-to-Runtime
Generates runtime configuration
Dynamic adapter loading
Code-to-Schema
Extracts schema from existing adapter
Migration, documentation
This specification primarily covers Schema-to-Code generators.
1.3 Scope
In scope:
Schema input format and validation
Generated code structure and artifacts
Licensing and provenance requirements
Language-specific template guidance
Out of scope:
Runtime behavior (see MCP-AQL Specification )
Adapter testing (see Conformance Testing )
Deployment and distribution

2.2 Schema Validation
Generators MUST validate input schemas:
Required fields - All required fields MUST be present
Type correctness - Field values MUST match expected types
Reference resolution - Type references MUST resolve
Name uniqueness - Operation and type names MUST be unique
Naming conventions - Names MUST follow snake_case convention
Validation error codes:

Example Message
Missing required field
SCHEMA_MISSING_FIELD
"Required field 'adapter.name' is missing"

SCHEMA_INVALID_TYPE

SCHEMA_UNRESOLVED_REF
"Type reference 'Repository' not found in types"

SCHEMA_DUPLICATE_NAME
"Operation 'get_user' defined multiple times in read endpoint"
Invalid naming
SCHEMA_INVALID_NAME

2.4 Schema Version Evolution
Version format rationale:
The schema_version field uses a simplified major.minor format (e.g., '1.0' ) rather than full semver:
Schema version ( schema_version: '1.0' ): Defines the input format the generator expects
Adapter version ( adapter.version: '1.0.0' ): Follows semver for the generated adapter's release lifecycle
This distinction separates concerns: schema format stability vs. adapter functionality evolution.
Evolution strategy:
Change Type
Version Increment
Breaking schema changes
Major ( 1.0 → 2.0 )
Removing required fields, restructuring endpoints
New optional features
Minor ( 1.0 → 1.1 )
Adding auth.config.scopes field
Clarifications, fixes
No change
Documentation updates, validation improvements
Backward compatibility requirements:
Generators SHOULD support multiple schema versions:
Current version - Full support (REQUIRED)
Previous major version - Conversion/migration support (RECOMMENDED)
Older versions - Reject with clear upgrade guidance (OPTIONAL)
Version handling in generators:
function validateSchemaVersion (schema) {
const supportedVersions = [ &#39;1.0&#39; , &#39;1.1&#39; ] ;
const deprecatedVersions = [ &#39;0.9&#39; ] ;
if (supportedVersions . includes (schema . schema_version )) {
return { valid : true } ;
if (deprecatedVersions . includes (schema . schema_version )) {
return {
valid : false ,
code : &#39;SCHEMA_VERSION_DEPRECATED&#39; ,
message : `Schema version &#39; ${ schema . schema_version } &#39; is deprecated` ,
migration_guide : &#39;https://mcpaql.org/docs/schema-migration&#39;
code : &#39;SCHEMA_VERSION_UNSUPPORTED&#39; ,
message : `Unknown schema version &#39; ${ schema . schema_version } &#39;` ,
supported_versions : supportedVersions
Migration guidance:
When schema versions change, the MCP-AQL project SHOULD provide:
Migration guide documenting required schema changes
Automated migration tool (when feasible)
Deprecation period of at least 6 months for major versions

3.2 Generated Code Requirements
Generated code MUST:
Implement CRUDE endpoints - All five endpoints with operation dispatch
Include introspection - Support for introspect operation
Handle errors correctly - Use structured error codes
Validate inputs - Parameter validation before API calls
Transform responses - Map target API responses to MCP-AQL format
Generated code SHOULD:
Include inline documentation/comments
Provide type definitions/interfaces
Include example usage in README
Generate test stubs for each operation

5.3 Fingerprint Calculation
Schema fingerprints MUST be calculated as follows:
Normalize the schema (remove comments, normalize whitespace)
Serialize to canonical JSON (sorted keys, no extra whitespace)
Calculate SHA-256 hash
Format as sha256:{hex_digest}
function calculateFingerprint (schema : AdapterSchema) : string {
// Recursively sort object keys for canonical JSON
function sortKeys (obj : unknown ) : unknown {
if ( Array . isArray (obj)) {
return obj . map (sortKeys) ;
if (obj !== null &amp;&amp; typeof obj === &#39;object&#39; ) {
const sorted : Record &lt; string , unknown &gt; = {} ;
for ( const key of Object . keys (obj) . sort ()) {
sorted[key] = sortKeys ((obj as Record &lt; string , unknown &gt; )[key]) ;
return sorted ;
return obj ;
const normalized = JSON . stringify ( sortKeys (schema)) ;
const hash = crypto . createHash ( &#39;sha256&#39; ) . update (normalized) . digest ( &#39;hex&#39; ) ;
return `sha256: ${ hash } ` ;

7. Command-Line Interface
7.1 CLI Invocation
Generators MUST provide a command-line interface with the following signature:
mcpaql-generate --schema &lt; path &gt; --target &lt; language &gt; [ options ]
7.2 Required Arguments
Argument
--schema , -s
Path to the input schema file (YAML or JSON)
--schema adapter.yaml
--target , -t
Target language/platform
--target typescript
7.3 Optional Arguments
--output , -o
Output directory for generated code
./generated
--config , -c
Path to generator configuration file
--output-format
Output format ( human or json )
--strict
Enable strict validation mode (fail on warnings, enforce all optional constraints)
--dry-run
Validate schema without generating output
--verbose , -v
Enable verbose output
--quiet , -q
Suppress non-error output
--version
Print generator version and exit
--help , -h
Print help message and exit
--verbose and --quiet are mutually exclusive. If both are specified, generators MUST exit with code 3 (Configuration error).
When both --config and individual CLI arguments are provided, CLI arguments MUST take precedence over configuration file settings.
7.4 Exit Codes
Generators MUST use consistent exit codes:
Generation completed successfully
Internal error
Unexpected error (assertion failures, uncaught exceptions)
Schema validation error
Input schema is invalid
Configuration error
Invalid generator configuration
I/O error
File read/write failure
Template error
Language template processing failed

8. Conformance Requirements
8.1 Generator Conformance
A conformant generator MUST:
Accept valid schemas without error
Reject invalid schemas with descriptive errors
Produce all required output files
Include valid licensing artifacts
Generate correct provenance information
Produce code that passes basic syntax checks
8.2 Generated Adapter Conformance
Generated adapters MUST:
Implement all five CRUDE endpoints
Support the introspect operation
Return discriminated responses ( success: true/false )
Use structured error codes from the specification
Handle missing/invalid parameters correctly
8.3 Conformance Testing
Generators SHOULD include conformance test generation:
# Run conformance tests on generated adapter
mcpaql-conformance test ./generated-adapter
See Conformance Testing Specification for test requirements.
